# Architecture

The game is a static website: React draws the screens, and the rules live in plain TypeScript functions with no React, so tests and balance bots run them directly.

```
src/
  main.tsx, App.tsx      entry point; App picks the screen for the current stage
  engine/                the whole game as one state machine
    types.ts             GameState, Stage, Action, all shared types
    flow.ts              next(state, action) -> state: the single reducer
    career.ts            ranks, badges, drill scores, mission log
    effects.ts, base.ts  the older card-based base game (kept, see "Legacy" below)
  sim/                   the base simulation
    types.ts             SimState, machines, crew, crops, storms
    rules.ts             EVERY number: power, use, limits, goals, risks
    engine.ts            createSim, runSol (one Mars day), nextSol, planning actions
    events.ts            surprises with choices
    eva.ts               spacewalk destinations and the pre-spacewalk checklist
    unlocks.ts           which system opens on which sol
  content/               words and data for the opening, Academy and storms
  data/solar-storms.json real NASA DONKI storms (generated by scripts/fetch-donki.mjs)
  screens/               one React component per stage
  ui/                    shared pieces: SimScene (the base illustration), Icon, Pip, Dialogue, Gauges
  services/              read-aloud (speech.ts) and on-device saving (storage.ts)
tests/                   Vitest tests and balance bots
scripts/                 storm data fetcher, icon generator
public/                  manifest, icons, offline service worker, privacy page, Android asset links
```

## One state, one reducer

`GameState` holds everything: the stage (title, badge, approach, landing, systems check, simulation...), the player, settings, career progress and the simulation (`state.sim`). Screens never change state directly; they call `dispatch(action)`, and `next(state, action)` in `engine/flow.ts` returns the new state. Actions that don't fit the current stage return the same state unchanged, which keeps the game safe from double clicks and stale buttons.

```mermaid
stateDiagram-v2
    [*] --> title
    title --> badge: START
    title --> academy: OPEN_ACADEMY
    badge --> approach: name + job chosen
    approach --> alarm --> briefing --> landingChoice
    landingChoice --> descent: CONFIRM_SITE
    descent --> touchdown --> damageReport
    damageReport --> simReady: START_SIMULATION (systems check)
    simReady --> sim: BEGIN_SIM
    sim --> title: RESTART
```

## The simulation (`src/sim`)

`createSim(state, seed)` builds the base from the landing: cracked panels, distance to ice, starting supplies, the crew (the player plus two crewmates in the other jobs), and a storm plan picked with a **seeded random generator**, so the same seed always gives the same mission (tests rely on this).

Each sol has two halves:

1. **Plan** (player): switch machines, give jobs, pick seeds, plan a spacewalk, answer any surprise.
2. **`runSol`** (engine): runs morning, day, evening and night. In each part of the sol:
   - solar panels add battery (less when cracked, dusty or in a dust storm, nothing at night);
   - machines draw power in priority order; when the battery runs short, the least important machines switch off first (`SHED_ORDER`);
   - the crew breathe, drink and eat; machines that ran make oxygen, scrub CO₂, recycle water, make fuel;
   - during the day, jobs happen, the solar storm (if any) adds radiation by where each astronaut is, and the spacewalk is resolved with its risk roll.
   
   Every change is written to a **ledger** with its cause, which becomes the evening report. A snapshot after each part of the sol drives the day-to-night animation.
3. **`nextSol`**: opens newly unlocked systems, rolls a possible surprise, and starts the next plan.

The mission ends early on an emergency (oxygen, water or food at zero, CO₂ at 3%, a crew member's health at zero) or a crew member reaching the 600 mSv radiation limit; otherwise after 7 or 10 sols with 1-3 stars.

## Drawing the base (`src/ui/SimScene.tsx`)

One SVG, 1200 × 680, drawn in layers: sky, terrain, cast shadows, buildings, crew, then a time-of-day light layer, weather, and finally everything that glows (windows, lamps, grow lights, readouts) so lights shine at night. Tank levels, the battery bar, crops and crew positions all come from the live readings. Objects lower on screen are scaled up for depth, and shadows follow the sun. The player can walk by tapping the ground or with W/A/S/D.

## Saving

`services/storage.ts` saves the player's name, settings, level and career in `localStorage` on the device only. Everything loaded is checked and cleaned (`readCareer`), so old or damaged saves can't break the game. Nothing is ever sent to a server.

## Tests

| File | What it covers |
|---|---|
| `flow.test.ts` | Every path through the opening, skip, level limits |
| `sim.test.ts` | Power, crops, CO₂, storms, surprises, repairs; balance bots over 40 seeds per role and site |
| `eva.test.ts` | Spacewalks, rover charge, checklist, risk; missions with walks beat missions without |
| `unlocks.test.ts` | What opens on which sol, locked jobs and machines |
| `career.test.ts` | Badges, points, ranks, drill scores, cleaning saved data |
| `base.test.ts`, `balance.test.ts` | The legacy card game |

## Deployment

Cloudflare Pages project `nasa-hack-26`, connected to `main` of `BinaryBandits-Hackathon/lunar-lifeline`. Build command `npm run build`, output folder `dist`. Every merge to `main` goes live in about a minute; other branches get preview links like `https://<branch>.nasa-hack-26.pages.dev`.

## Legacy

`engine/base.ts`, `content/cards.ts`, most of `content/rules.ts` and the screens `Board`, `CardScreen`, `Result` and `Ending` are the first, card-based version of the base game. The simulation replaced it and the game no longer reaches those screens, but the code and its tests are kept for reference.

Before removing them in a cleanup, keep what the simulation still uses: `STORMS` and `nextRandom` from `engine/base.ts`, `strengthFromKp` from `content/rules.ts`, and `applyEffects` / `START_GAUGES` from `engine/effects.ts` (used by the opening).
